# Database rules (PostgreSQL, SQLAlchemy 2.0, Alembic)

## Modeling
- The ER model is in guide §7.1. Keep releases, deployments, approval requests and decisions, health checks, rollback events and audit logs as **separate records**. Don't merge them into status columns.
- Use UUID primary keys and `timestamptz` (UTC) timestamps.
- Use **CHECK constraints** for status, decision, role and `operation_type` values. Mirror them in Python enums.
- Required unique constraints: `workspaces.slug`, `(application_id, version)` on releases, `webhook_deliveries.delivery_id`.
- Required indexes: `deployments (environment_id, created_at)`, `deployments (status, created_at)`, `deployments (release_id)`, `approval_requests (status, requested_at)`.
- Foreign keys on every relationship. Never cascade-delete deployment, approval or audit history.
- `releases.image_digest` is the artifact identity. Treat a release row as immutable after registration (except build status and release notes).

## Migrations
- One Alembic revision per logical change, autogenerated **and then reviewed by hand** (check enums, constraints and server defaults).
- Every migration has a working `downgrade()`.
- Stay **backward-compatible for one release** (expand → migrate → contract), so the ReleaseGuard app can be rolled back.
- Before committing: `alembic upgrade head` on an empty database, then `alembic downgrade -1`, then `alembic upgrade head`, then `alembic check`.

## Transactions and concurrency
Transaction boundaries, the approval transaction, advisory locks and `SKIP LOCKED` live in `backend.md` (it also loads for `services/`, which owns transactions). Repositories never commit.
