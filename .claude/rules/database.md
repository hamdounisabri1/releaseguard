# Database rules (PostgreSQL, SQLAlchemy 2.0, Alembic)

## Modeling
- The ER model is in guide §7.1. Keep releases, deployments, approval decisions, deployment events, health checks and audit logs as **separate records**. The deployment is the aggregate: its approval state, `policy_snapshot` and `rollback_of_deployment_id` live on it (ADR-0003). Don't add tables that duplicate a deployment's status.
- Every tenant table has `workspace_id`. Child tables reference their parent with a composite FK, e.g. `(application_id, workspace_id)` → `applications (id, workspace_id)` (which needs `UNIQUE (id, workspace_id)` on the parent).
- Use UUID primary keys and `timestamptz` (UTC) timestamps.
- Use **CHECK constraints** for status, decision, role and `operation_type` values. Mirror them in Python enums.
- Required unique constraints: `workspaces.slug`, `(workspace_id, repository_id)` on applications (a partial unique index over `status = 'active'`, so archiving frees the repository), `(application_id, environment_type)` on environments, `(application_id, version)` on releases, `(deployment_id, reviewer_id)` on approval decisions, `webhook_deliveries.delivery_id`, `jobs.dedupe_key`, `(workspace_id, idempotency_key)` on deployments (partial, where not null).
- **Single active deployment:** `UNIQUE (environment_id) WHERE status IN ('queued','deploying','verifying')` on deployments. Keep the status list in sync with the Python `ACTIVE_STATUSES` constant.
- Required indexes: `deployments (environment_id, created_at DESC)`, `deployments (workspace_id, status, created_at DESC)`, `deployments (release_id)`, `health_checks (environment_id, checked_at DESC)`, `jobs (run_after) WHERE status = 'pending'`, `environments (next_check_at)`, `audit_logs (workspace_id, target_type, target_id, created_at DESC)`.
- **Append-only:** a trigger rejects `UPDATE`/`DELETE` on `audit_logs` and `deployment_events`. Create it in the same migration as the table.
- `environments.current_deployment_id` ↔ `deployments.environment_id` is a cycle: add that FK in a later step of the migration, nullable.
- Foreign keys on every relationship. Never cascade-delete deployment, approval or audit history.
- `releases.image_digest` is the artifact identity (`CHECK (image_digest ~ '^sha256:[0-9a-f]{64}$')`). Treat a release row as immutable after registration (except release notes).
- Retention: only scheduled `health_checks` (14 days) and `done` jobs (7 days) are ever deleted, by the worker.

## Migrations
- One Alembic revision per logical change, autogenerated **and then reviewed by hand** (check enums, constraints and server defaults).
- Every migration has a working `downgrade()`.
- Stay **backward-compatible for one release** (expand → migrate → contract), so the ReleaseGuard app can be rolled back.
- Before committing: `alembic upgrade head` on an empty database, then `alembic downgrade -1`, then `alembic upgrade head`, then `alembic check`.

## Transactions and concurrency
Transaction boundaries, the approval transaction, the single-active-deployment rule and `SKIP LOCKED` live in `backend.md` (it also loads for `services/`, which owns transactions). Repositories never commit.
